# 任务包模板

任务包决定这个循环的实际吞吐。**它写得含糊，后面每一环都在还债。** 每个任务包只对应一个小任务和一个新的 Codex session；不得把整个无人值守任务队列塞进同一个包。

存成文件后通过 stdin 传给 codex（见 `cli-gotchas.md`）。下面九节按顺序写，缺一节就会在某个环节返工。

---

## 1. 角色与工作目录

```
你是本项目的实现工程师。本次是一个全新的 session，只负责 <任务 ID>。
当前工作目录位于长期集成分支 <分支名>，基于 <基线/当前 commit>。
<已完成的前置任务清单> 已经通过主 agent 验收并形成 checkpoint。
```

**已完成清单和当前 commit 要写**——新 session 没有前序聊天记忆，它们决定 Codex 会不会重复造已有的东西或误改已验收部分。

## 2. 背景

```
请先读这几处，那是本次任务的需求来源。不要通读其他文档：
- <文件路径> 第 X 节（<一句话说明为何是依据>）
- <文件路径> 第 Y 节
再读 <功能拆分文档> 中 <功能项 ID> 的行。
```

**"不要通读"是硬要求。** 不加这句，它会花大量上下文读完整套文档，而且抓不住重点。只点出与本次相关的章节，并说明每节为什么是依据。

## 3. 本次范围

```
## 本次范围（只做这两项）
- **F02.03** 预览世界并定位待补事项
- **F02.04** 申请公开并冻结本次审阅内容

**不要做**：<相邻但不在本切片的功能，逐个列出>
```

范围边界靠这段守。**列出的"不要做"要具体到功能项 ID**，不要只说"不要做无关的事"。

同时写明依赖边界：允许读取已完成任务的代码，但不得顺手重构已形成 checkpoint 的部分；发现前置实现确实阻塞本任务时，在报告里指出，不自行扩大范围。

任务包范围冻结不禁止 Claude Code 重新细分。实现者发现任务过大、上下文不足或连续没有进展时，应保存已有代码并报告：已完成且有证据的部分、剩余验收条件、建议切分边界。由 Claude Code 停放现场并通过 `run-state.py split` 更新任务图；实现者不得自行添加任务、丢弃验收标准或把原队列塞进同一 session。重拆后的任务包引用父任务 ID 和原始验收条目，最后一个子任务覆盖组合验收。

## 4. 由架构冻结的决定（本模板的核心）

这是实现方式的冻结层。写要点：

- **编号**，每条一个决定
- **给出理由或出处**（引用设计文档的行），让它理解约束的来源而非机械执行
- **显式声明不可协商**，但留一个出口：

```
以下契约约定**已经锁定**。你的职责是把它们落成代码、schema 和测试；
如果你认为某条在实现上不可行或自相矛盾，**不要自己改，在最终报告里
指出并说明理由**。
```

这个出口很关键。实测中它据此报告了错误码表的真实缺口（客户端错误被兜底成 503），而不是自行发明一个码绕过。

**容易做错的语义要显式点出**，例如：

| 维度 | 取值 | 常见错误 |
| --- | --- | --- |
| `format` | text/image/video/mixed | — |
| `genre` | novel/script/… | ❌ 把"小说"当 format |
| `canon_relation` | official_story/based_on_canon/parallel | ❌ 把"正式故事"当 format |

**把"错误示例"写进去**比只写正确取值有效得多。

## 5. 交付物

```
1. 数据库迁移：<表名与关键约束>
2. 端点：<路径>
3. 测试：单元测试 / 集成测试（需真实 PostgreSQL，由主 agent 执行）
```

## 6. 关键：必须能被回退验证

**这一节决定了你这个循环有没有牙齿。** 固定句式：

```
下面性质，**删掉相应用实现后测试必须变红**。请逐条执行并在报告中写明：
1. **<不变量名>**：<怎么破坏> 后，"<哪条测试>" 必须失败
2. ...
3. ...
```

要求它**自己先做一遍并报告**，但确定性验证阶段仍要独立重做（见 `verification-gates.md`）。

三条是经验上的合适数量——多了它会把回退做成流水账，少了覆盖不住。

**破坏方式要具体到可执行**。"让 X 失效"太模糊；"移除 A 与 B 两个条件""把 `candidate_visual` 映射改为 `official_visual`"才是可执行的。

## 7. 方法提醒（把踩过的坑前置）

本仓库已反复踩过、写进任务包后 codex 能自己避开的：

```
**重要方法提醒（本项目已反复踩过，务必照做）**：
- `packages/*` 的 `exports` 指向 `./dist/index.js`，`pnpm exec vitest` 不会自动
  重新构建。改完 `src/` 必须重新构建再跑，并在**函数/方法级别**确认 dist 真的变了。
- 文本补丁会打中**同名同形的孪生方法**。替换前**先按类名与方法名切片**，
  并在切片内**断言待替换语句出现次数为 1**。
- **注入位置要选函数体内部的锚点**，不要用 `index('{')` 之类会命中参数类型或签名的写法。
- **注入的判定条件必须真实存在**（曾出现注入不存在的字段名导致条件恒假、回退"无效"）。
- **每个根脚本要独立从零验证**（各自跑前清空全部 `dist/` 与 `*.tsbuildinfo`）。
- 请在**设置与不设置 `DATABASE_URL` 两种情况下**都跑一遍 `pnpm test:unit`。
- 需要真实数据库的回退验证，**明确标注"需主 agent 在集成测试上验证"**，
  不要用跑不到的测试假装通过。
```

最后一条尤其重要：它防止"跑不到的测试"被当成通过。

## 8. 沙箱说明

```
- **跑不了 Docker 和 PostgreSQL**，需要数据库的集成测试由主 agent 执行，
  不要尝试修基础设施。
- 单元测试、`pnpm install` / `build` / `typecheck` / `lint` 可以跑。
- 不要 commit、push 或开 PR（沙箱写不了 `.git`）。
```

第一句省掉能省十几分钟无用功。

## 9. 报告要求

```
## 完成后用中文报告
1. 创建/修改了哪些文件
2. 你运行的每条验证命令及真实输出
3. 三条回退验证各自怎么做、结果如何（含函数级 dist 确认）
4. <本次特有的问题>
5. 需要确定性验证阶段执行的测试清单
6. 没把握或与文档有出入的地方
7. 给下一个新 session 的最小交接信息（只写代码状态和未决风险，不复述全过程）
8. 若范围过大：仍未覆盖的验收条件、已保存的成果和建议切分边界

如实报告，不要粉饰。
```

**"如实报告，不要粉饰"要写。** 实测中它据此主动报告了"沙箱无数据库因此未执行""某性质尚未得到证明""不能声称 X 已端到端可用"——这些都是你后面验收的线索，隐瞒比暴露代价大得多。

## UI QA 分类

任务若改变 Web、桌面或其他用户可见流程，登记状态时使用 `--task-kind ui`；`qa.mode=ui_tasks` 会自动标记 `qa_required`。其他模式按配置要求显式选择 `--qa-required` 或 `--no-qa`。另写独立 QA 包，不要把实现者报告直接改名当 QA 包。QA 包应从用户视角描述完整流程、账号/seed、允许和禁止动作、断言及截图 checkpoint。具体模板与双重验收见 `qa-testing.md`。

## 附：打回时的反馈写法

用 `codex exec resume`。结构：

```
独立 reviewer 提交 finding，主 agent 已完成证据仲裁。<一句总体判断>，但有一处需要修改。

## 我验证通过的部分——不要改动
<逐条列出，防止它连带改坏已验证的东西>

## 需要修改：<问题标题>
### 现象
<失败断言原文 / CI 报错原文>
### 复现
<具体命令>
### 根因
<你定位到的原因，含文件与行>
### 要求的最终状态
<可判定的验收条件>
## 沙箱提醒 / 完成后报告
```

**"不要改动"那段不能省。** 没有它，返工常常顺手重构掉已验证通过的部分。
