# 验证门禁

**核心原则：不采信报告，也不重复整份 review。** 实现报告和 reviewer verdict 都只是证据。独立 reviewer 负责读取完整 diff 找语义缺陷；主 agent 只仲裁结构化 findings，并用确定性命令补上 reviewer 和实现者看不见的路径。用户可见流程通过这些门禁后，还要按 `qa-testing.md` 做 Codex 黑盒 UI QA、截图审计和 CC 独立复测。

主 agent 默认只加载 `review.json`、任务包中的验收条件和验证命令结果，不加载完整 diff、完整事件流或长测试日志。只有 finding 的证据冲突、门禁失败需要定位，或 reviewer 被判定不可靠时，才读取相关文件切片。

为控制 Claude Code 主上下文，验证命令的完整输出写入任务运行目录，主会话只接收命令、退出码、失败断言和证据路径。宿主支持独立验证子 agent 时可委托其执行这些门禁；最终仲裁仍由 Claude Code 完成，不能把子 agent 的自述当作测试证据。压缩后按 run-contract、state 和当前验收记录接续，不重做已经有有效证据且目标未变化的全部历史检查。

这些门禁先证明代码和契约，再做 UI QA；UI QA 不能替代单元/集成/安全验证，代码阅读也不能替代真实 UI 操作。

## 六道门禁

### 门禁 1：回退验证（独立重做）

**唯一不依赖信任任何一方的验收方式。** 由主 agent 用精确脚本/命令执行；只把退出码、失败断言和必要切片带回主上下文。

步骤：

1. 打开目标方法，**按类名与方法名切片**（不是全文件搜索——会打中孪生方法）
2. 在切片内**断言待替换语句出现次数为 1**，不等就停下来看清楚
3. 替换/删除实现
4. **重新构建受影响的包**
5. **在函数级确认 dist 里那段代码真的变了**（`grep` 方法切片，不要只看全文件计数）
6. 跑那条测试，**看它红**
7. 恢复，重新构建，看它绿

任一步跳过都会得到假信号。以下是实测踩过的全部假信号：

| 假信号 | 根因 | 现象 |
| --- | --- | --- |
| 回退后测试仍绿 | 改了 `src/` 没重新构建，测试读到旧 `dist/` | 差点报出一个不存在的缺陷 |
| 回退后测试仍绿 | 补丁打中了**同名同形的孪生方法**（同文件里三处相同语句） | 全文件计数变了，目标方法没变 |
| 回退后测试仍绿 | 注入的**判定条件引用了不存在的字段**，条件恒假 | 编译通过，注入从不执行 |
| 回退后测试仍绿 | 跑错了测试文件——该性质的行为级验证在集成测试里，我跑的是字符串断言测试 | 换了文件立刻成立 |
| 回退后测试仍绿 | 回退的是内存实现，测试走的是 PostgreSQL 仓储 | 换对组合立刻成立 |
| 注入后编译失败 | 注入点选在**函数签名**里（`index('{')` 命中了参数类型） | 需改到函数体内锚点 |

### 门禁 2：不变量可追溯

每条关键约束能指到设计文档的具体条目（跨流程规则编号、数据模型约束、主文不变量序号）。指不到的，要么是新增约束（那就该补进文档），要么是实现自行发明的东西。

### 门禁 3：接口符合已冻结契约

对照任务包里冻结的决定逐条核。**自造字段名、自造错误码、自造状态值**都是信号——说明它绕过了契约，后面会不一致。

### 门禁 4：权限检查在服务端

不该有的东西：客户端隐藏按钮当权限、`if (isAdmin)` 就地放行、把主体身份从请求参数里读。

**独立 grep 一遍**：把"客户端声称的身份"相关的头/字段名全仓搜一次，确认只出现在测试文件里（作为"尝试伪造"的输入）。实测中这一步确认了整条身份伪造面被彻底移除。

### 门禁 5：幂等与并发有覆盖

有写入的地方问三件事：重复请求会不会产生第二次副作用？并发时谁会赢、输的一方拿到什么？撤权/状态变化后未完成的写入会怎样？

### 门禁 6：没把"看起来对"当成"验证过"

自问：这条结论我是**跑出来的**还是**读出来的**？读出来的标注成"未验证"。

## 独立攻击（reviewer 未必会要求，但必须做）

**自己构造载荷直接打实现，不跑仓库内测试。**

实测：要求 codex 写安全渲染器时，仓库测试覆盖了若干攻击向量；我独立构造 19 个载荷（标签注入、属性逃逸、协议混淆、实体编码、NUL 截断、大小写混写）直接打渲染器，确认 0 穿透。仓库测试只覆盖其中一部分。

构造载荷时注意**判据要精确**——第一轮我的正则匹配到了"已转义文本里的字面 `onerror=`"和"渲染器自己生成的安全标签"，报出 13 个假阳性。正确判据是：只看标签内的属性、只看未转义文本区。

## 环境验证（本地全绿不等于 CI 能过）

### 每个根脚本独立冷启动

```bash
clean() {
  find packages apps -type d -name dist -not -path '*/node_modules/*' -exec rm -rf {} + 2>/dev/null
  find packages apps -name '*.tsbuildinfo' -not -path '*/node_modules/*' -delete 2>/dev/null
}
clean && pnpm test:unit
clean && pnpm test:integration
clean && pnpm build
clean && pnpm typecheck
```

**每次跑前都清空。** 实测：连着跑时，前一条命令构建的产物被后一条复用，掩盖了后一条缺失的构建步骤——本地两次全绿，CI 红。

同源陷阱还有：**本机残留的 `dist/` 让命令通过，而 CI 全新克隆没有它**。

### 集成测试连跑两次

第二次必须也全绿。实测中一套测试共用数据库时，两次运行失败点不同（一次是 `outbox_events` 残留，一次是 `world_memberships` 外键）——**不幂等的套件早晚会红，而且报错点会误导人**。

跑完检查有没有残留 schema / 残留数据。

### CI 必须真跑过再合

CI 是第三个独立视角。实测中它抓到过两次本地看不见的问题。

## 打回时检查"是否复发"

发现缺陷后问：**这是个例还是模式？**

实测中"遗漏某个包的构建"复发三次（`database` → `database` → `ui`），根因是四个脚本各自手工枚举包名。前两次都只补了缺失的那一个；第三次才要求把手工清单换成通配构建，根治。

**要求系统性修复，不接受补丁。** 同时要求它证明修的是根因，例如"新增任何 `packages/*` 后无需再改这些脚本"。

同理，测试隔离问题不接受"再补一个 delete"，要求统一的隔离策略，并且**明确禁止放宽断言来掩盖状态泄漏**——测试变红时最省事的做法是把断言改松，那样问题就被藏起来了。
